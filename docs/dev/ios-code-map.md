# iOS code map

One codebase builds both the desktop app (macOS / Windows / Linux) and the iOS app. This document explains which code is shared, which code is desktop-only, and how the two are kept apart. The rule: **desktop behavior does not change**. On iOS, desktop-only code is neither compiled nor called.

## Rust (`src-tauri/`)

### How the code is kept apart

- `tauri-build` sets `cfg(desktop)` or `cfg(mobile)` automatically for the target platform. Mark all desktop-only code with `#[cfg(desktop)]` and all iOS-only code with `#[cfg(mobile)]`. Code without a mark is shared.
- **Dependencies:** `tauri-plugin-updater` and `tauri-plugin-process` are under `[target.'cfg(not(any(target_os = "ios", target_os = "android")))'.dependencies]` in `Cargo.toml` (the metadata of both plugins lists iOS support as none). `tauri-plugin-single-instance` was already included only on Windows/Linux. The macOS PDF dependencies (objc2-\*) and the Windows/Linux webview dependencies were already split by OS. `opener` and `dialog` support iOS and stay shared. The attachment parsers `pdf-extract`, `calamine`, `zip` and `quick-xml` are pure Rust, so they are shared too.
- **Command registration:** `lib.rs` has a single `invoke_handler`. Shared commands are in the first half of the `generate_handler!` list. Desktop commands are in the second half, each with `#[cfg(desktop)]` in front of it (tauri-macros supports attributes on single commands). So on iOS these commands are never registered.
- **Builder:** The shared part is in `run()`: the opener and dialog plugins and `PendingOpenPaths`. The desktop part is in `desktop_builder()`: the updater/process plugins, the state for windows, dragging, sessions and the chat window, `on_window_event`, and `setup` (argv, session restore, CLI, menu bar, window size).
- **Permissions (capabilities):** `capabilities/default.json` is shared and contains core, opener, dialog and event. `capabilities/desktop.json` is limited to desktop with `"platforms": ["linux","macOS","windows"]`. It holds the permissions for window chrome, full screen, always-on-top, the title, and updater/process. Without this split, the iOS build fails because it cannot find `updater:default`.
- **Configuration:** `tauri.conf.json` adds `bundle.iOS.minimumSystemVersion = "16.0"`. `tauri.ios.conf.json` is merged into the iOS configuration and does two things:
  1. It keeps only one main window, without the desktop window options, and marks it `"create": false` as on the other platforms. (When Tauri merges, it replaces the whole `windows` array, so every platform config that has `windows` must include this.) `build_main_window` in `lib.rs` creates the window after settings are loaded, so the iOS webview also gets the boot script (see [Settings and UI state](#settings-and-ui-state) below).
  2. It sets `createUpdaterArtifacts: false`.

  Do not turn off `macOSPrivateApi` in the iOS config. If you do, the CLI rewrites the tauri features in `Cargo.toml`.

## Frontend (`src/`)

- `src/platform/os.ts` adds `isIOSPlatform()` and `isDesktop()`. On iPhone, `navigator.platform` is `iPhone`. iPad uses the desktop user agent by default and reports `MacIntel`, so `navigator.maxTouchPoints > 1` tells an iPad apart from a real Mac.
- `src/platform/capabilities.ts` is **the only place that defines platform policy**. Callers only read the flags here. They never check the operating system themselves. The flags are `isDesktopApp`, `canUseWindows` (multiple windows, window titles, closing/destroying windows, session restore), `hasAppMenu`, `canDragTabsBetweenWindows` (desktop and macOS), `canDetachChat`, `canToggleFullscreen`, `canAutoUpdate`, `canExportPdf`, `canExportWithPandoc`, `canRevealInFileManager`, `canPickFolder` and `canInstallCliCommand`.
- Where the flags are used:
  - App: setting the window title, reporting session paths, destroying the window when the last tab closes, Zen mode full screen, dragging tabs out
  - Elsewhere: `useTabDragMerge` (drag a whole window to merge it), `startup-restore`, `useAppUpdate`, `useDetachedChat`, the pop-out buttons in MilkdownEditor and AgentPanelView, the Settings panel (new document mode, session restore, CLI, update button, workspace folder, open in file manager, expand to window), ProjectBar, `export-doc`, full screen in `app-menu-actions`, and `window-chrome` (`data-window-chrome="mobile"` on iOS)
- In `platform/ipc.ts`, all desktop commands go through `desktopQuery` (returns an empty value on iOS) or `desktopAction` (rejects on iOS). This is the last line of defense: a call site that was missed still cannot reach Rust.
- Desktop behavior does not change at all. On desktop every flag is equal to the old check. `canDragTabsBetweenWindows` is the old `isMacPlatform()`.
- Mod in shortcuts: `modIsMeta()` in `src/platform/os.ts` follows the same rule as ProseMirror. Mac, iPhone and iPad all count as Cmd. On iPhone, `navigator.platform` is `iPhone`. iPad reports `MacIntel` in WebKit's desktop-class mode and `iPad` in mobile mode (see `isIOSPlatform`). When it reports `iPhone` or `iPad`, `isMacPlatform()` returns false, and Cmd would not work with a hardware keyboard. So the app shortcuts (`utils/shortcuts.ts`) and the editor's Mod+Enter (`block-keys-plugin.ts`) use `modIsMeta()` instead.

## Settings and UI state

Since 0.9.7, settings, UI state and the two histories are no longer in the webview's localStorage. They are in JSON files owned by Rust (`src-tauri/src/settings.rs`; for the list of files and the paths on each platform, see [storage.md](storage.md)). iOS and desktop share the same code:

- **Files:** In the app container under `Library/Application Support/com.catvinci.textus/`. `settings.json` holds every item in Settings. `ui-state.json` holds where the interface was left. On iOS this includes the recently opened documents (`iosRecentDocuments`) and the document list view (`documentListView`). It also holds tutorial progress, whether the AI panel is open and its width, and the cached interface colors of an imported theme (`themeChrome`). There are also `chat-history.json` and `clipboard-history.json`. As with recent documents, chat history stores paths of documents inside Documents as relative paths (`documents:...`, `src/platform/documents-path.ts`) and joins them to the current Documents folder when reading. Absolute paths saved by older versions are rewritten once on load. So after a reinstall or an update, old chats stay grouped with their documents. Debug builds write `*.dev.json`. The frontend reads and writes through `src/storage/ui-state.ts` and `settings/SettingsContext.tsx`.
- **Boot script:** Before the webview loads the page, Rust injects an init script (`src-tauri/src/boot.js`, joined with a snapshot by `settings::boot_script`). It sets `window.__BOOT__` (a snapshot of settings and UI state, which the frontend reads synchronously in `src/storage/boot.ts` instead of the old localStorage). Before the first frame, it also applies the appearance, the content width, `lang`, the imported theme's CSS and interface colors, and custom CSS. So the default theme does not flash at startup. The snapshot is taken when the window is created. After a page reload, the frontend reads the live values from Rust again.
- **Writes:** The frontend sends only the changed fields (`settings_patch`, `ui_state_patch`; histories one entry at a time). Rust debounces for 250 ms, then writes to disk atomically, and writes any remaining changes on quit. Every settings change is sent at once (custom CSS is sent on every keystroke). Only zoom waits until a pinch or wheel gesture has stopped for 400 ms before it saves. Before a window closes, every close path first waits for writes still on their way to reach Rust (`src/storage/pending-writes.ts`). iOS never closes windows. When the app goes to the background (`visibilitychange`), the frontend sends any pending writes (zoom) at once.
- **First launch after upgrading from 0.9.6:** If `settings.json` does not exist yet, the window starts with `legacyImport`. It hands the old data in localStorage (including the iOS `levis-ios-recent-documents` and `levis.documentListView`) to Rust once (`settings_import_legacy`). localStorage is left as it is.

## File access (iOS)

The design is in the "文件访问方案" (file access plan) section of [2026-10-ios-plan.zh.md](../archive/2026-10-ios-plan.zh.md). The code is in three places:

- **Native plugin `src-tauri/plugins/textus-files`:** The Swift implementation is in `ios/Sources/TextusFilesPlugin.swift`. The Rust part only forwards calls and is compiled only on iOS (it is a workspace member and an empty crate on desktop). It provides:
  - picking files and picking folders;
  - reading, writing and listing directories within the granted scope, with reads and writes through NSFileCoordinator;
  - saving grants as bookmarks. At startup, `restoreFolderAccess` (`src/main.tsx`) reopens previously chosen folders through `remembered`. Without this, the AI cannot read the project folder after a restart;
  - `begin_access`: keeps access to a folder for the whole session and returns a plain path;
  - `share`: the system share sheet (see [iPhone interface](#iphone-interface) below);
  - `read_data`: reads a file within the granted scope as base64. It is used for images at relative paths next to the chosen document (`scopedImageSrc`, `editor/images/image-plugin.ts`). A document chosen on its own grants access to that file only, so its images can only be read if they are inside a chosen folder.
- **Frontend `src/platform/ios-files.ts`:** Wraps the plugin calls. If a document chosen in the Files app is actually inside the app's Documents folder, it is turned back into a plain path, so the same file is not opened twice under two spellings. The `fs` layer in `platform/ipc.ts` routes by path: `file://` URLs (files the user chose) go through the plugin. All other paths (the app's own Documents folder, all desktop paths) go to the Rust commands as before. Callers do not care about the platform.
- **Project folder:** On iOS, after `ai.pickWorkspaceRoot` picks a folder, it calls `begin_access` and passes the plain path to Rust. The access grant is valid for the whole process, so the code in `ai/project.rs` that reads `.textus/` and project files needs no change.
- **Configuration:**
  - `src-tauri/PrivacyInfo.ios.xcprivacy`: the privacy manifest. It declares two kinds of "required reason APIs": UserDefaults (the plugin stores bookmarks) and file timestamps (to check whether a document was changed outside the app). Without it, App Store Connect rejects the upload. `tauri.conf.json` does not control this file. `scripts/ios-prepare.sh` copies it into the project after `tauri ios init`. It must run right after init. If xcodegen runs again later, it also adds the built library to the resources, which causes "Multiple commands produce libapp.a";
  - `src-tauri/Info.ios.plist`: makes the Documents folder appear in the Files app, supports opening files in place, and registers "Open with Textus" for Markdown;
  - `capabilities/ios.json`: the plugin permissions on iOS;
  - Documents opened from the Files app (`RunEvent::Opened`) keep their `file://` URL on iOS and are read and written through the plugin.

## Building for iOS (needs a Mac and Xcode)

```sh
rustup target add aarch64-apple-ios aarch64-apple-ios-sim
brew install xcodegen          # if you skip this, tauri ios init also tries to install it
npm ci
npx tauri ios init             # generates src-tauri/gen/apple (not committed to the repo)
sh scripts/ios-prepare.sh      # right after init: adds the privacy manifest and has xcodegen regenerate the project
npx tauri ios dev              # run on a simulator or a device
npx tauri ios build            # build; a device needs a development team set in bundle.iOS.developmentTeam
```

The `ios` job in CI (`.github/workflows/ci.yml`) runs on `macos-26`. It first selects the newest released Xcode 26 on the runner explicitly. It only accepts real folders whose names are plain version numbers, and skips betas and symlinks that point to betas. This is the same Xcode the TestFlight upload uses (`ios-release.yml` explains why). Then it runs `npx tauri ios init --ci`, `scripts/ios-prepare.sh` and `npx tauri ios build --ci --debug --target aarch64-sim --no-sign`. This builds for the simulator, without signing, and needs no secrets. For now, the required `rust` check does not depend on this job.

On Linux you can only run `cargo check`. The C code in dependencies such as `ring` needs the Apple SDK. To skip the C build, set a fake `CC_aarch64_apple_ios` / `AR_aarch64_apple_ios` and add a fake `xcrun`. This only checks that the cfg separation is correct (it does not link).

## iPhone interface

- **Styles:** All in `src/mobile/styles/`, imported through `index.css` (from `main.tsx`). The desktop style sheets are not touched. The rules are at the top of `index.css`: every selector starts with `:root[data-window-chrome="mobile"]`. This prefix gives the rules enough specificity to win over the desktop rules without depending on load order (the editor styles are in a lazy-loaded chunk and arrive after the main entry). Rules for all touch devices (iPhone and iPad) are at the top level. Phone layout rules are inside `@media (max-width: 760px)`, the same width as `usePhoneLayout()`. Files are split by area:
  - `base.css`: 44pt title bar, 20pt icons, the font stack (`-apple-system`, `system-ui` and `ui-monospace` show Chinese and Japanese as boxes in iOS 26 WebKit), 16px inputs, no focus ring on touch, and the page background extended under the status bar and the Home indicator;
  - `sidebar.css`: the drawer and 44pt rows;
  - `chrome.css`: dialogs, menus, the find bar and the tab bar;
  - `editor.css`: a light theme-colored background for whole-node selection instead of ProseMirror's default #8cf blue outline, the table "+" bars, and the code block language;
  - `ai-sheet.css`, `quick-ask-dock.css`, `composer.css`, `settings.css`.

  Styles for components that exist only on phones (`ActionSheet`, `PhoneNavBar`, `KeyboardToolbar`, `DocumentList`) sit next to the component.

- **Phone layout switch:** `ui/usePhoneLayout.ts` (iOS and width ≤ 760px). A wide iPad keeps the desktop popup menus and dialogs.
- **Select boxes:** On iOS, `ui/Select.tsx` is a native `<select>` (laid transparently over a button with the same look). A tap opens the system picker.
- **Action sheets:** `ui/ActionSheet.tsx` is a UIKit-style list of actions at the bottom of the screen, with **Cancel** in its own block. At phone width, `ContextMenu` renders as an action sheet automatically. So a long press on a file, the document **⋯** button, the project folder menu and "Save changes?" are all action sheets.
- **Menu:** The button on the left of the title bar opens `buildMobileMenu` (`app/app-menu-model.ts`). It is one flat list with only document actions, find and replace, the sidebar and Settings. Source mode, typewriter mode, Zen mode and the two help items are in Settings (**Editor & Appearance › View** and **General › Help**), and they toggle through the same events as the menu items. iOS has no `menu.rs`, so `emitMenuEvent` (`platform/menu-events.ts`) turns a menu id into the event of the same name that `useMenuBridge` listens for, and sends it to this window. The target must be a `WebviewWindow`. A bare label becomes `AnyLabel`, and on iOS both the window and the webview are named main, so the event arrives twice and toggle actions cancel each other out.
- **Keyboard:** `KeyboardFit.swift` (also in the textus-files plugin, started by the plugin's `load(webview:)`) shrinks the webview to sit above the keyboard when the keyboard opens. It also turns off the webview's own scrolling and bounce. Otherwise WebKit pushes the whole page up and the title bar moves off screen. The page's resting position is not 0 but minus the top safe area height (`pinToTop`). It is corrected again when the user comes back from another app. Otherwise the title bar and the text end up under the status bar. `platform/mobile-viewport.ts` only sets `maximum-scale=1`, so the page does not zoom in when an input gets focus.
- **Saving and opening:** **Save** on a new document writes it straight into Documents, using the suggested name, with a number added if the name is taken (`newDocumentPath`). When no document is open, the file tree shows Documents and has no "up one level". **New File** adds a tab on iOS (there is no window to open). The last opened document is stored in `iosRecentDocuments` in `ui-state.json` (in localStorage in 0.9.6 and earlier; see [storage.md](storage.md)). Documents inside Documents are stored as relative paths, because a reinstall or an App Store update changes the container path (so does reinstalling over an existing install on the simulator).
- **Document list:** **Documents**, at the top of the menu, opens `mobile/DocumentList.tsx`. It lists opened documents by time (`recentIOSDocuments`, at most 30, stored in `ui-state.json`, with relative paths for documents inside Documents; the first one is the document reopened at launch). Changes to the list (open, remove, rename) are queued and run one after another (`updateRecents` in `document/ios-recents.ts`), so when two documents open at the same time, neither entry overwrites the other. The choice of list or grid view is also stored in `ui-state.json` (`documentListView`). A tap opens a document. **⋯** or a long press shows the actions: Open, Share, Rename, Delete. Documents in the Textus folder are handled by Rust's `rename_entry` / `delete_entry` (`commands/documents.rs`, registered only on iOS; the path must be inside Documents). A document chosen on its own from the Files app grants access only to the file, not to its folder, so it can only be opened, shared or removed from the list. After a rename, open tabs follow the new path. After a delete, the tab keeps its content and becomes unsaved.
- **Sharing:** **Share…** in the menu, and a long press in the document list or on a sidebar file, call the plugin's `share`. It copies the document to a temporary folder and opens the system share sheet (AirDrop, Messages, Mail, Save to Files). An unsaved document is saved first. A long press in an iOS web view does not fire the contextmenu event, so `utils/hooks/useLongPress.ts` times long presses itself.
- **Menu check marks:** Toggle menu items (sidebar, source mode, typewriter mode, Zen mode; the in-app menu on desktop Windows/Linux also has the AI panel and split view) carry `checked` and show ✓ when on (`MenuChecks`, passed in by App). When the phone menu opens, the editor loses focus, so the keyboard and the system "Paste | Format" bubble close and do not cover the menu.
- **Keyboard toolbar:** `mobile/KeyboardToolbar.tsx` appears above the keyboard while editing a document. It has heading, bold, italic, list, quote, code block, and "✦ AI" (opens Quick Ask at the cursor; phones have no shortcuts, so this is the only way in). Bold and italic are `md_span` nodes, not marks, and are handled by `toggleSpan` in `editor/marks/span-commands.ts`. Buttons act on touchend and cancel the default action, so they do not take focus from the editor. They are all 44pt and scroll sideways when they do not fit. The toolbar changes with the cursor: in a table it shows add row, add column, delete row, delete column and delete table (`TABLE_ACTION_EVENT`). After an image is tapped, it shows width presets and delete (`IMAGE_ACTION_EVENT`). The last button, **⋯** (`EDITOR_MORE_EVENT`), replaces the context menu, which cannot open on a phone. It lists, in an action sheet, the context menu items that the toolbar does not have (`buildPhoneMoreItems` in `editor-menu.ts`). So at phone width the table hover "+" bars and the image drag handles are hidden, and the code block language picker grows to 44pt (`mobile/styles/editor.css`).
- **Grammar suggestions:** Phones have no hover. A tap on an underline (the caret lands inside it, right after a touch) opens an action sheet. Its title is the explanation, and its options are the suggested text and **Ignore**. The desktop hover popover does not change.
- **AI bottom sheet:** At phone width, Textus AI is a bottom sheet. By default it takes about 55% of the height, and the document stays visible above it. A tap on the grip at the top (`AgentPanelSheetGrip`) switches between half and full screen. Drag up to expand, drag down to collapse or close. A wide iPad still shows it as a column on the right.
- **Quick Ask:** At phone width it does not sit inside the document (the keyboard would cover that block, and the web view cannot scroll). Instead it docks at the bottom of the screen, right above the keyboard (`docked` on `InlineChat`, styles in `mobile/styles/quick-ask-dock.css`). The top row quotes the selected text (or shows "At the cursor" when nothing is selected), with new chat, move to the full chat, and close next to it (all 44pt). The middle holds the reply and accept/reject, up to about 40% of the screen, and it scrolls. The input box is at the bottom. The change preview is still drawn in the document, and `ai/chat/quick-ask/quick-ask-dock.ts` scrolls the document so the change sits above the dock. While the dock is open, the keyboard toolbar is hidden and the dock takes its place above the keyboard.
- **AI input box:** Quick Ask and the bottom sheet share `ChatComposer`. On phones, Ask / Edit / Plan is a segmented control, all buttons are 44pt, and the `/` skill and `@` file suggestion rows are selected on touchend (`ui/tap.ts`, so they do not take focus from the input). No :hover state stays after a tap (`mobile/styles/composer.css`).
- **Settings:** The same panel as desktop (`settings/SettingsPanel.tsx`). There is no separate phone page. Every row is "name + control" (`SettingRow` in `settings/sections/controls.tsx`). Only the few rows that really need it have a description. At phone width the panel fills the screen, the categories become tabs at the top, and **Done** is in the top-right corner. Styles that only change size and layout are in `mobile/styles/settings.css`. There are five categories: General, Editor & Appearance, Textus AI, Shortcuts and Privacy. Phones do not show Shortcuts, so the other four fit on one screen. The AI page is ordered "connect first, then features", and each model sits next to the feature it drives:
  1. Connection (provider, sign-in and credentials, network proxy, model list)
  2. Writing assistance (continuation, grammar check, writing model)
  3. Textus AI chat (switch, chat model, default mode, web search)
  4. Writing rules and skills (workspace folder, agent.md, skills, global config folder)
  5. Advanced settings, collapsed

  When chat is off, the last two groups are hidden. The model and workspace rows are in `settings/sections/agent.tsx`. Providers and credentials are in `settings/sections/providers.tsx`. The AI name in the interface is defined only once, as `AI_NAME` in `i18n/names.ts`, and every string that contains the name is built from it (the 1.0 rename to Textus changed only this line). Settings field names (such as `agentModels`) stay the same, and old settings are read as usual. On phones, closing Settings does not return focus to the document (`ui/useModalDialog.ts`), so the keyboard does not pop up again. Inputs that the program reads as is, such as URLs, model names and proxy addresses, have auto-capitalization and autocorrect turned off (`VERBATIM_INPUT` in `settings/sections/controls.tsx`). iOS capitalizes the first letter, even with a hardware keyboard, and providers do not accept a model name like "Mock-model". **Done** is also a single accent-colored word in the iPad Settings dialog.

- **AI completion:** Phones have no Tab key. A tap on the gray suggestion accepts it (`touchend` in `ghost-text-plugin.ts`), and the description in Settings changes to "tap to accept".
- **First launch:** After the user picks a language, the tutorial does not start automatically (the tutorial teaches keyboard shortcuts).
- **Tests:** `e2e/phone.spec.ts` uses Chromium's phone viewport and touch emulation to check the drawer, the full-screen AI panel and tap-to-accept. Real iOS WebKit behavior (keyboard, fonts, file picking) was checked by hand in the simulator with idb.

## Not handled yet

- The PKCE flow of `codex_login` / `claude_login` depends on a local localhost callback server. Whether it completes after the app goes to the background still needs testing on a real device.
- Pasting an image into a document chosen from the Files app: `save_pasted_image` still writes next to the document with a plain path, which fails for `file://` documents. Documents inside Documents are not affected.
- Closing the last remaining tab: on iOS this currently does nothing (the tab stays).
